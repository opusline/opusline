# spatie/laravel-data v4

## The one decision rule for THIS repo (read first)

The OpenAPI spec is generated by **Scramble**, which powers the typed TS client
(`@opusline/api-client`) the web app consumes. laravel-data is used **end to
end** at the HTTP boundary; documentation is covered by two mechanisms:

- **Requests**: type-hint a Data class in the controller method
  (`login(LoginData $data, ...)`). laravel-data validates on resolution, and
  free Scramble's native rules extraction reads the class's `rules()` method -
  producing rich schemas (formats, max lengths, `password_confirmation` from
  the `confirmed` rule). **Convention: declare validation in an explicit
  `rules()` method, not attributes** - that is what Scramble reads.
- **Responses**: controllers return `response()->json(SomeData::from(...))`
  with an explicit status code (laravel-data's auto-201-on-POST magic is
  deliberately bypassed). Schemas come from the custom extension
  `app/OpenApi/SpatieDataToSchema.php` (registered in `config/scramble.php`),
  which reflects the constructor: scalars, nullable, backed enums,
  DateTimeInterface, nested Data. **Not covered**: lazy properties,
  include/exclude, name mapping, paginated collections - extend the extension
  before using those in a documented response.

There are NO FormRequests and NO Eloquent API Resources in this app; do not
reintroduce them. After changing any Data class used at the boundary, run
`pnpm generate-api` and check `apps/api/openapi.json` before frontend work.

## Creating Data objects

```php
class PostData extends Data
{
    public function __construct(
        public string $title,
        public PostStatus $status,          // native enums cast automatically
        #[Date]
        public ?CarbonImmutable $published_at,
    ) {}
}

PostData::from(['title' => 'Hello', 'status' => 'draft', ...]); // array
PostData::from($postModel);                                     // model attributes
PostData::collect($posts);                                      // iterable -> collection of Data
```

- `from()` is polymorphic: arrays, models, requests, other Data objects.
- Custom creation: add static `fromString(string $x)`, `fromModel(Post $post)`
  etc. — `from()` picks the matching magic method by parameter type.
- `empty()` returns a null-filled blueprint (`PostData::empty(['status' => 'draft'])`).

## Validation

Rules are **inferred from property types**: non-nullable → `required`, typed →
`string`/`integer`/`boolean`/`array`, native enum → `enum`, nullable → `nullable`.

```php
class SongData extends Data
{
    public function __construct(
        public string $title,
        #[Max(20)]                          // validation attributes refine inference
        public string $artist,
    ) {}

    public static function rules(ValidationContext $context): array
    {
        return ['title' => ['required', 'string', 'unique:songs']]; // overrides
    }
}

SongData::validateAndCreate($input);   // validates, throws ValidationException
```

Validation runs automatically when a Data object is resolved from a request
(controller injection) or created via `from($request)` — but per the decision
rule above, in this repo that path is reserved for non-documented internals;
documented endpoints use FormRequests and hand the validated array to
`Data::from()` (creation from trusted arrays does NOT validate — that is by
design; validate at the boundary, trust inside).

## Transformation / output

- `toArray()` / `toJson()` transform recursively (dates → strings, enums → values).
- `all()` keeps original types (no transformation).
- `Spatie\LaravelData\Resource` base class = Data minus validation/authorization,
  for output-only shapes.
- Lazy properties defer expensive loads:
  `public Collection|Lazy $posts` + `Lazy::create(fn () => PostData::collect($author->posts))`,
  then `$data->include('posts')`. Only relevant for internal/undocumented output.

## Name mapping

```php
#[MapName(SnakeCaseMapper::class)]      // class-level, both directions
class ContractData extends Data { ... }

#[MapInputName('record_company')]       // property-level, input only
public string $recordCompany;

#[MapInputName('artists.0.name')]       // dot-notation extraction
public string $artist;
```

`MapInputName` = creation, `MapOutputName` = transformation, `MapName` = both.
Global defaults go in `config/data.php` (`name_mapping_strategy`) — this app has
not published the config; publish only when a global strategy is actually needed.

## Conventions in this codebase

- Data classes live in `app/Domain/<Context>/Data`, one class per shape, named
  by role (`RegisterUserData`, not `RegisterRequestData`).
- Constructor property promotion, `declare(strict_types=1)`, no `final` (matches
  existing classes), plain `public` properties.
- Passwords and other to-be-hashed values cross as plain strings; hashing is the
  model cast's job (`'password' => 'hashed'`).
- Every new Data class used by an Action gets exercised by that Action's test;
  standalone mapping subtleties (custom `from*`, mapping attributes) get their
  own unit test.
