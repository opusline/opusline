# Audit — 2026-08-28

Second audit. Branch: `main` (clean, at `984e701`, v0.19.0). Scope: `apps/api`,
`apps/web`, `apps/storybook`, `packages/ui`, `packages/api-client`, repo
tooling/CI/ops/release/i18n. Method: orientation pass + six parallel deep reviews
+ cross-cutting synthesis; every P1 and every load-bearing P2 claim was
re-verified against source (or against the GitHub API) before being written here.

Since the last audit: **61 commits, 1,923 files, +94k lines.** Four new API
domains (Bank, Deadlines, Declarations, Documents), five new web features
(bank, treasury, declarations, deadlines, revenue), full en/fr i18n, a
release-notes pipeline, a three-database CI matrix, and parallel Pest.

## Executive summary

The last audit's findings were addressed with unusual thoroughness — **all seven
P1s are genuinely closed**, along with nine of the twelve P2s, and several fixes
are better than what was suggested. The codebase absorbed a 94k-line expansion
without losing its authorization model, its locking idiom, its float-free money
layer, or its story discipline. What this audit finds is almost entirely one
shape: **the repo's philosophy is invariants-as-tooling, and every consequential
finding sits in a blind spot of that tooling.** `main` requires a pull request
but requires **no status checks at all**, so the three-database matrix, the
drift guard, the i18n guard and the 535-test Storybook suite are advisory.
Beneath that, each guard has a specific hole that maps exactly onto a live
defect: the a11y gate runs only in dark mode and the light theme was never
contrast-tuned; the i18n guard matches only accented characters and unaccented
French copy ships on the main screen; nothing at all checks the
"frontend never does money arithmetic" rule and it has regressed in three new
places; `ArchitectureTest` is thirteen lines and does not assert the
auth-on-routes invariant the whole security design rests on. Fix the merge gate
first — it is a settings change, and it is what makes every other fix stay
fixed. Self-hosting, the stated core product value, still has no deployment path
of any kind and is escalated as a repeat finding.

## Findings

### [P1] `main` requires a pull request but requires no status checks — every guarantee in this repo is advisory

- **Where**: GitHub ruleset `20240781` on `~DEFAULT_BRANCH`
  (`gh api repos/:owner/:repo/rulesets/20240781`); `.github/workflows/ci.yml`
- **What**: The active ruleset contains exactly three rules — `deletion`,
  `non_fast_forward`, and `pull_request` with `required_approving_review_count: 0`.
  There is **no `required_status_checks` rule**, `bypass_actors` is empty, and
  `gh api repos/:owner/:repo/branches/main/protection` returns 404 (no classic
  protection either). Verified directly against the API. So the six CI jobs, the
  sqlite/MySQL/Postgres Pest matrix, `scripts/generated-artifacts.sh`,
  `scripts/i18n-guard.sh`, `scripts/release-notes-guard.sh` and the 535-test
  Storybook browser suite can all be red while the merge button stays green —
  with zero required approvals to catch it.
- **Why it matters**: This is the load-bearing finding of the audit. The repo has
  invested heavily in guards that are *correct*, and then made every one of them
  optional. It is also why the other findings exist: several are exactly the
  class of regression a required check would have blocked. For an AGPL project
  inviting outside contributors — who have no pre-push hook until they run
  `pnpm install` — it means CI signal has no teeth at all.
- **Suggested fix** (S): Add a `required_status_checks` rule to the existing
  ruleset listing the JS lane, the API static-analysis lane, the three API test
  matrix legs, the generated-artifacts drift job, the Storybook build, the PR-title
  check and the release-note-fragment check, with
  `strict_required_status_checks_policy: true`. Settings-only, no code.

### [P1] The frontend computes money in three new places — the invariant regressed, and the DTOs are why

- **Where**:
  - `apps/web/src/features/week/lib/week-money.ts:69-73` —
    `(entry.valuedDayFraction ?? 0) * mission.rate.amount` then `Math.round(...)`,
    rendered as an HT total at `week-summary-tiles.tsx:217`.
  - `apps/web/src/features/deadlines/components/deadline-timeline.tsx:293-301` —
    `Math.round((fiscal.amount.amount * 10_000) / fiscal.rateBp)` to reverse-engineer
    the URSSAF base out of the contribution.
  - `apps/web/src/features/missions/components/new-mission-page.tsx:55-57,195-206` —
    `URSSAF_PROVISION_RATE = 0.26`, `MONTHLY_BILLABLE_DAYS = 20`,
    `MONTHLY_BILLABLE_HOURS = 140`, producing a monthly / provision / "net estimé".
- **What**: Three independent violations of the project's single most-stated
  cross-cutting rule, all in features written *after* the last audit removed the
  previous two (`billableAmountCents`, the client-side TTC sum — both confirmed
  gone). The week tile multiplies a **float** day fraction by a rate, which is
  precisely what `EntryRounding::billedDayFraction()`'s docblock forbids in
  writing: *"a float is fine for display but cannot multiply a rate … 1/3 of a
  day has no float representation to round from."* The deadline back-division is
  not invertible — the API produced that amount with `->multiply($rateBp)
  ->divide(10_000, ROUND_HALF_UP)` (`CollectedInvoices.php:79-89`) — and
  `deadline-timeline.test.tsx:56-63` enshrines the artefact. The hardcoded 26 %
  is wrong for every ACRE account, while the real per-account
  `effectiveContributionRateBp` is displayed two screens away
  (`fiscal-settings-form.tsx:82`) and a story fixture already uses 2820.
- **Why it matters**: The root cause is not web-side indiscipline — it is that
  the DTOs do not carry the figures the screens need, so the browser fills the
  gap. `CollectedInvoices::htCents()` already exists and is documented as *"the
  URSSAF declaration's base"*; `ValueTrackedTime::measure()` already returns
  per-entry Money; neither is on a DTO. Meanwhile `/declarations` shows the
  authoritative server figure, so the same user can read two different "encaissés"
  numbers in one app, and an ACRE freelance sees a "net estimé" off by ~15 % on
  the screen where they decide whether to take a mission.
- **Suggested fix** (M): Close the contract gaps — add `base: ?MoneyData` to
  `FiscalDeadlineData`, add a value field to `TimeEntryData` (or a week-summary
  endpoint), and either add a projection endpoint or thread
  `effectiveContributionRateBp` + `workdayMinutes` into the mission route. Then
  delete the three computations. Because this class has now regressed twice,
  pair it with a guard: a Biome `noRestrictedSyntax` rule (or a small AST test)
  banning arithmetic operators on `.amount` outside `lib/billing.ts`.

### [P1] The light theme was never contrast-tuned, and the a11y gate can only see dark

- **Where**: `apps/storybook/.storybook/preview.ts:46` (`defaultTheme: "dark"`),
  `:23` (`a11y: { test: "error" }`); `packages/ui/src/styles/globals.css:11-85`
  (`:root`); offenders at `button.tsx:10,21`, `badge.tsx:12,14,16,17,18`,
  `input.tsx:7`, `chip.tsx:106`, `segmented-control.tsx:20`, `help-tip.tsx:21`,
  `tabs.tsx:63`, `signature-pad.tsx:389`
- **What**: Contrast recomputed independently during this audit — the numbers
  reproduce exactly. Dark passes AA everywhere measured; **light fails in 15
  component-level pairs**:

  | Pair | Light | Dark | Need |
  |---|---|---|---|
  | `primary-foreground` on `primary` (default Button, brand Badge, pressed segment) | **3.72** | 4.87 | 4.5 |
  | `primary` as text (`Button variant="link"`) | **3.42** | 4.93 | 4.5 |
  | `muted-foreground-5` on `muted` (Input / SignaturePad placeholder) | **3.00** | 4.70 | 4.5 |
  | `muted-foreground-4` on `background` (quiet Badge, HelpTip) | **3.51** | 5.30 | 4.5 |

  The gate itself is real and enforcing — `test: "error"` genuinely calls
  `toHaveNoViolations()`, and the committed log shows 154 files / 535 tests
  against headless Chromium. But `withThemeByClassName` pins `defaultTheme:
  "dark"` and **not one story anywhere overrides `globals.theme`** (grepped
  across `packages/ui`, `apps/web`, `apps/storybook`: zero hits). All 535 axe
  runs execute against `.dark` only.
- **Why it matters**: Light is the default for any user on a light-mode OS —
  `apps/web/src/lib/theme.ts` ships `system | light | dark`, cookie-persisted and
  server-backed. They get a primary CTA at 3.72:1. There is a sharp irony here:
  fixing the last audit's dark-palette P1 is what created the condition that
  hides its mirror image, because the tuned theme is the only one the gate sees.
  CLAUDE.md declares accessibility non-optional.
- **Suggested fix** (M): First make the gate see both themes — a second vitest
  project or a `globals: { theme: "light" }` sweep — which turns every row above
  into a failing test. Then retune the light `:root`: `--primary-foreground`
  should go dark-on-amber (`#1f1b18` on `#ba7517` = 8.2:1) or `--primary` should
  darken; `button.tsx:21` should use the **already-defined and entirely unused
  `--link` token** (4.59:1) instead of `text-primary`; `--muted-foreground-4/-5`
  need roughly two steps darker in light.

### [P1] Hardcoded French ships a French UI to English users, and both guards are structurally blind to it

- **Where**: `apps/web/src/features/week/components/week-toolbar.tsx:74`

- **What**: Seven user-visible strings on the app's primary screen are literals

  decisions: **`week_today` already exists in both catalogs** (`en.json` →

  rigorous (see finding below) — this is the web half catching up.

### [P1] The account-currency lock predicate has drifted behind the columns it protects

- **Where**: `apps/api/app/Domain/Users/Models/User.php:187-204`
  (`hasLockedCurrency()`), `apps/api/app/Domain/Settings/Actions/ChangeAccountCurrency.php:36-45`,
  `apps/api/app/Domain/Settings/Models/UserSettings.php:156-159`,
  `apps/api/app/Domain/Missions/Models/Mission.php:142-143`,
  `apps/api/app/Domain/Missions/Data/CreateMissionData.php:28`
- **What**: `hasLockedCurrency()` documents the invariant as *"fixed the moment
  any amount is stored in it … so every stored amount provably shares one
  currency"*, and checks four things: a priced mission, any invoice, any bank
  statement, any personal transfer. `ChangeAccountCurrency` then nulls
  `treasury_buffer_cents` and `bank_balance_cents` because *"carrying their cents
  into the new currency would silently re-denominate them."* Two money-cast
  columns are in neither list:
  - **`user_settings.cfe_expected_cents`** — money-cast at `UserSettings.php:159`,
    added later than the other two (migration `2026_08_21_000002`), neither
    checked nor cleared. An account whose only stored amount is an expected CFE
    can change EUR→USD and the €480 the user typed becomes `Money(48000, 'USD')`
    in the provisions and on the deadline board.
  - **`missions.reference_daily_rate_cents`** — money-cast at `Mission.php:143`,
    with no `required_with` tying it to `rate` (`CreateMissionData.php:28`). A
    Fixed mission carrying only a reference rate has `rate_cents IS NULL`, so the
    predicate returns false while `missions.currency` already holds the old code.
- **Why it matters**: The entire aggregation layer (`SummarizeRevenue`,
  `SummarizeTreasury`, `ComputeBankProvisions`) sums `Money` without currency
  guards *precisely because* this predicate is trusted. A figure entered in one
  currency gets silently relabelled as another, and the CFE one flows straight
  into the "combien je peux me virer" headline. The two existing clearings are
  tested; neither of these columns is.
- **Suggested fix** (S): Add both columns to the predicate and clear
  `cfe_expected_cents` alongside the buffer. Better, make the predicate derive
  from one declared list of money-bearing columns — the same reasoning
  `GenerateFiscalDeadlines::signature()` already applies ("taken from the output
  rather than from a list of the inputs … forgetting it is invisible").

### [P1] Still no self-hosting path, on the product's stated core value — repeat finding, escalated

- **Where**: `apps/api/compose.yaml:6,25,61,95,149-150,174`;
  `apps/api/.env.example`; `apps/web/src/lib/api.ts:8,12`; `README.md:9-22`;
  `git ls-files | grep -iE 'dockerfile|deploy|nginx|caddy|helm|k8s'` → **zero matches**
- **What**: Unchanged since `audit-2026-08-14.md:309`, which raised it as P2.
  `compose.yaml` is a pure dev Sail stack — it *builds from
  `./vendor/laravel/sail/runtimes/8.5`* (so a host `composer install` must precede
  `docker compose`), bind-mounts the whole tree at `.:/var/www/html`, and hardcodes
  MinIO credentials `sail`/`password`. `.env.example` is a dev env
  (`APP_ENV=local`, `APP_DEBUG=true`, `DB_PASSWORD=password`) copied verbatim by
  `scripts/bootstrap.sh`. Env vars a self-hoster provably needs are absent from it
  although `config/**` reads them: `SESSION_DOMAIN`, `SESSION_SECURE_COOKIE`,
  `SESSION_LIFETIME`, `OCTANE_HTTPS`, `APP_PREVIOUS_KEYS` — behind a
  TLS-terminating proxy, the missing two break Sanctum's cookie flow as
  intermittent 419s. `apps/web` hard-binds to same-origin `/api` and `/sanctum`
  with no `VITE_*` escape hatch — the right call for cookie auth, but it imposes a
  reverse-proxy requirement documented nowhere. `docs/` contains only `audits/`.
  Meanwhile `.github/ISSUE_TEMPLATE/bug_report.yml` offers "Self-hosting / Docker"
  as an area.
- **Why it matters**: It is the single differentiator in the pitch
  ("self-hostable alternative to Kimai") and the only thing an AGPL license is
  *for*. Until it exists there are no external reproductions, no external
  contributors, and no backup/restore/upgrade story — and open issue #78
  ("Instances & sauvegardes") is blocked on it. Per the audit's repeat-offender
  rule this escalates from P2 to P1.
- **Suggested fix** (L): A multi-stage `Dockerfile` (build `web` → static,
  `composer install --no-dev` → FrankenPHP runtime, no bind mounts, no `vendor/`
  in the build context), a `compose.prod.yaml`, a `.env.production.example` with
  the five missing vars, a Caddy/nginx snippet showing `/` → static and
  `/api` + `/sanctum` → app, and `docs/self-hosting.md` covering first boot,
  backup and upgrade.

### [P2] `ArchitectureTest` asserts almost nothing — including not the auth model the security design rests on

- **Where**: `apps/api/tests/Unit/ArchitectureTest.php` (13 lines, verified in
  full); `apps/api/app/Http/Deadlines/Controllers/DeadlineCalendarController.php:32`
- **What**: The whole arch suite is `preset()->php()`, `App\Domain` not→uses
  `App\Http`, and `toUseStrictTypes()`. Nothing asserts CLAUDE.md's actual API
  rules. In particular nothing asserts that every `/api` route except the ICS feed
  is behind `auth:sanctum` — that invariant lives purely in the fact that each of
  the 14 route files happens to open with a `Route::middleware('auth:sanctum')`
  group (verified 14/14). A fifteenth file, or a route declared after the group
  closure, is silently public and the suite stays green. The thin-controller rule
  already has a live violation the arch test cannot see: `DeadlineCalendarController::show`
  performs `$user->settingsOrFail()->update([...])` inline — the only
  `->update(`/`->create(`/`->delete(` anywhere under `app/Http/`, on an
  unauthenticated GET, using bare `now()` rather than the account clock.
- **Why it matters**: The repo's own security model is stated as *"there is no
  policy layer: ownership is enforced by the route binding"*
  (`InvoiceRouteBindingTest.php:7-10`). When authorization is structural, the
  structure needs a test — otherwise the only thing between a new route file and
  a public endpoint is the author remembering.
- **Suggested fix** (S): Add a test walking `Route::getRoutes()`, filtering
  `api/`, asserting `auth:sanctum` in `gatherMiddleware()` with an explicit
  allowlist of exactly `api/ping` and `api/calendar/{token}.ics`. This is the
  highest-value single test the repo could add. Add
  `arch()->expect('App\Http')->not->toUse(DB::class)` and move the heartbeat into
  a `RecordCalendarFetch` action.

### [P2] Foreign-key columns are unindexed on Postgres and SQLite — both are in the CI matrix

- **Where**: `apps/api/database/migrations/2026_08_03_000002_create_missions_table.php:22`,
  `2026_08_13_000001_create_invoices_table.php:24-25`,
  `2026_08_16_000002_create_bank_movements_table.php:24,26`
- **What**: `foreignIdFor(...)->constrained()` creates the column and the FK
  constraint but emits **no index**. InnoDB auto-creates one; Postgres and SQLite
  do not — and `.github/workflows/ci.yml` runs the suite against all three, so the
  schema is claimed portable while its index coverage silently is not. Unindexed:
  `missions.client_id`, `invoices.client_id`, `invoices.mission_id`,
  `bank_movements.bank_statement_id`, `bank_movements.invoice_id`. All are read on
  hot paths (`ClientController::index` `with('missions')`,
  `SummarizeClientRevenue.php:117,141`, the join in `SummarizeBankAccount.php:120`
  which runs on *every* bank summary). Worse than the reads: `clients` and
  `missions` use `restrictOnDelete`, so on Postgres every `DELETE /api/clients/{client}`
  sequential-scans `missions` and `invoices` to prove the restriction. The
  neighbouring explicit composite indexes on the same tables
  (`(user_id, issued_on)`, `(user_id, booked_on)`, …) show the author knows the
  pattern — these slipped.
- **Why it matters**: An engine-dependent performance cliff that CI cannot catch
  (fixtures are tiny) and that surfaces in a self-hoster's Postgres after a couple
  of years of invoices. Open issue #159 ("performance pass for the API") lands here.
- **Suggested fix** (S): One migration adding the five indexes. Consider a unit
  test asserting every `foreignIdFor` column is the leading column of some index,
  so the next FK cannot repeat it.

### [P2] Applying a rate to money has six spellings, the URSSAF formula exists twice, and `ValueTrackedTime` has no test

- **Where**: `ComputeInvoiceAmounts.php:12-19`, `SummarizeRevenue.php:33,239`,
  `CollectedInvoices.php:34,85-88`, `CfeSchedule.php:38-49`, `CfeBareme.php:71-77`,
  `ComputeBankProvisions.php:226`; `ValueTrackedTime.php:92-133`
- **What**: Three related weaknesses in the layer that matters most.
  1. Six forms of "apply basis points to money". Four stay in `Money` with
     explicit `ROUND_HALF_UP`; **two drop to raw ints and truncate** —
     `CfeBareme::estimate` (`intdiv($base * RATE_BP, 10_000)`) and
     `ComputeBankProvisions::cfe` (`intdiv((int) $expected->getAmount() * $month, 12)`)
     — operating on the *same* CFE figure that `CfeSchedule` handles as `Money`.
     `BASIS_POINTS = 10_000` is redeclared privately in five classes.
  2. The URSSAF cotisation formula — the most fiscally consequential line in the
     app — exists in two independent copies (`SummarizeRevenue:239` and
     `CollectedInvoices:85-88`). They agree today; only one has a half-cent test;
     nothing would fail if they diverged.
  3. `ValueTrackedTime` is the single place tracked minutes become money and feeds
     three screens, and **no test file references it**. Every feature test that
     exercises it uses figures that divide exactly (11 days × 55,000 cents). The
     two sibling formulas both have explicit midpoint tests
     (`ComputeInvoiceAmountsTest.php:16-20`, `RevenueTest.php:239-251`) — this one
     has none, while `pricedDayFraction` divides by `workdayMinutes` so most real
     invoices land on a fraction of a cent.
  Worth noting for accuracy: the "explicit rounding mode" rule holds for every
  `divide()`, but **no** `multiply()` passes one. Those are integer × integer on
  minor units so nothing is wrong today — but the convention is not uniform, and
  moneyphp's default *is* `ROUND_HALF_UP`, so a dropped argument would be invisible.
- **Why it matters**: Untested critical math, not untested glue — and open issues
  #109/#110 (auto-fill URSSAF and TVA papers) build directly on these figures.
- **Suggested fix** (M): One `Money` rate helper carrying the rounding mode once,
  one shared `BASIS_POINTS`, one `shareBp()` helper; bring `CfeBareme` and
  `ComputeBankProvisions::cfe` back onto `Money`. Add `ValueTrackedTimeTest`
  pinning cents at the boundaries (hourly odd minutes, a non-dividing workday, a
  half-cent midpoint, zero-rate and fixed-price). Add an arch test asserting no
  `->divide(`/`->multiply(` outside the helper.

### [P2] The CFE barème guess enters the treasury headline unlabelled, and its test asserts the opposite

- **Where**: `ComputeBankProvisions.php:204-234` (esp. `:216`),
  `BankProvisionData.php:74-87`, `BankProvisionsData.php:14`,
  `PriceFiscalDeadlines.php:121-138`, `CfeBareme.php:55-78`,

- **What**: `ResolveExpectedCfe` returns an `ExpectedCfe` carrying `isEstimate`,

  and failing both `CfeBareme::estimate()` — a national ballpark the class itself
  calls *"explicitly a rough idea"*. Both consumers get the same object.
  `PriceFiscalDeadlines` propagates `isEstimate` all the way to the timeline badge.
  `ComputeBankProvisions::cfe()` takes `->amount` and throws the provenance away;
  `BankProvisionData` has no field to carry it. Two artefacts went stale as a
  result: `BankProvisionsData.php:14` still documents the CFE provision as *"null
  until the user names an amount"*, which stopped being true when
  `ResolveExpectedCfe` landed; and `BankProvisionsTest.php:203` — named *"provisions
  nothing for the CFE until the user names an amount"* — passes only because its

  `EXEMPTION_FLOOR_CENTS = 500_000`. The first test in the same file arranges
  495,000 cents: 5,000 short of flipping the behaviour.
- **Why it matters**: `SummarizeTreasury.php:85-87` computes

  collects €5,000, an unlabelled guess (≈€110/yr, rising to ≈€1,050) enters that
  headline — while the same number is labelled honestly one screen away. The test
  that should have caught the change asserts the opposite of what the code does.
- **Suggested fix** (S–M): Add `isEstimate` to `BankProvisionData` and thread it
  through; fix the docblock; rewrite the test as *"provisions a barème guess once
  the account has collected enough"* plus a real "nothing to go on" case.

### [P2] Form-control borders fail WCAG 1.4.11 in both themes — the one a11y failure axe can never report

### [P2] Money amounts and free-text notes have no upper bound at the boundary

- **Where**: `apps/api/app/Domain/Shared/Data/MoneyData.php:18-19`,
  `SignedMoneyData.php:22-23`, `CreateClientData.php:29`, `UpdateClientData.php:35`,
  `CreateMissionData.php:34`, `UpdateMissionData.php:36`
- **What**: CLAUDE.md requires explicit validation on anything security-relevant,
  and this codebase does that unusually well elsewhere. Two gaps.
  `MoneyData::$amount` carries `#[IntegerType, Min(1)]` and **no `Max`**;
  `SignedMoneyData::$amount` carries only `#[IntegerType]`. So
  `amountHt = 9223372036854775807` validates, `ComputeInvoiceAmounts::ttcFor` then

  CLAUDE.md flags billing/invoice math for extra care.
- **Suggested fix** (S): `#[Max]` on both amount properties (a sane cap such as

## Aligned-and-healthy

Protect these — several are better than the last audit found them, and two are
things most projects this size never get right:

- **Authorization survived a 94k-line expansion intact.** Every route parameter in
  all 14 route files was traced to its binding: `OwnedRouteBinding` on six models,
  `scopeBindings()` on the one nested group, documents resolved through the owning
  relation, the ICS feed behind a 64-char random token with a route pattern and a
  throttle. Every `#[Exists]`/`#[Unique]` on a foreign id carries a
  `WhereConstraint('user_id', new AuthenticatedUserId)`. `assertUnauthorized`
  appears in 55 feature files, covering every new domain. **No P1 in the entire
  boundary layer.**
- **Timezone discipline is now complete and tested at the hard edges.** Zero uses
  of the framework's `before_or_equal:today`; every fiscal date rule goes through
  `BeforeOrEqualAccountToday`, which *throws* rather than falling back to UTC when
  there is no authenticated user. Tested at 23:30 UTC on 31 December from Paris and
  from a UTC account, and a CRA sent at 22:30 UTC landing in the next month.
- **No float money anywhere in the API.** Every `float` in `app/Domain` is a day
  count, an external percentage, or a display fraction.
  `EntryRounding::billedDayFraction()` returns an exact `[numerator, denominator]`
  specifically so a rate never multiplies a float — and the overtime clamp the last
  audit asked for now lives inside it, so the CRA and the money path cannot
  diverge. This is the invariant that matters most and the API holds it perfectly.
- **`CfeSchedule::balance()` = `total − instalment`.** The two halves of a split
  CFE can never fail to sum to the whole, whatever the rounding. That is the right
  way to split money — it removes a bug class instead of testing for it.
- **The bank parsing layer refuses ambiguity instead of guessing.** `AmountParser`
  rejects `1,23.45`; `StatementDate::fromParts` uses `checkdate` to refuse
  DateTime's silent `32/01 → 01/02`; `Camt053StatementParser` clears libxml's
  process-wide error buffer because Octane would accumulate it;
  `ComputeRunningBalances` derives every balance from one anchor rather than
  trusting per-line file balances.
- **One lock idiom, applied uniformly**, and `AccountCurrency`'s three-tier design
  (request rule + two under-lock re-check helpers) with the race written down.
  Finding P1-5 is a gap in the *predicate*, not in this mechanism.
- **Query invalidation is exemplary.** `lib/query-invalidation.ts` has no
  hand-written partial keys, and `query-invalidation.test.ts:29-33` asserts the
  hey-api `{ _id }` key shape **against the real generated builders**, so a
  regeneration that moves it fails the suite instead of turning invalidations into
  silent no-ops. This directly closes a prior-audit finding, and closes it better
  than suggested.
- **No optimistic updates in the newer features — deliberately.** Every write
  returns the recomputed aggregate and the route writes it straight into the cache.
  There is no rollback to be missing and no second GET per action; a better answer
  than optimistic-with-rollback for this app.
- **Zero `localStorage`/`sessionStorage` in production code**; theme persistence
  uses a cookie for FOUC with the server as source of truth.
- **Calendar-date handling is disciplined and now falsifiable.** Every
  `new Date(string)` in the app is on an instant, verified caller by caller — not
  one `new Date("YYYY-MM-DD")`. The `browserTodayCalendarDate` vs
  `accountTodayCalendarDate` split (tracking clock vs fiscal clock) is a genuinely
  sharp distinction applied consistently, and the TZ lanes now run date-sensitive

- **The drift guard is one script called from both doors**, never forked. Same for
