# Audit — 2026-09-14

Third audit. Branch: `main`, at `93458480`, v0.27.0. Scope: `apps/api`,
`apps/web`, `apps/storybook`, `packages/ui`, `packages/api-client`, repo
tooling/CI/ops/release/i18n. Method: orientation pass + six parallel deep
reviews + cross-cutting synthesis; every P1 and every load-bearing P2 claim was
re-verified against source, against recomputed contrast numbers, or against the
GitHub API before being written here.

Since the last audit: **112 commits, 1,694 files, +99.6k/−10.1k lines**,
v0.19.0 → v0.27.0. Three new API domains (Expenses, TwoFactor, Passkeys), a
Déclarations rework with annual returns, receipt OCR, a self-hosting path with
backup/restore, Dependabot auto-merge, and Sentry on both halves of the stack.

## Executive summary

The 2026-08-28 audit's findings were closed with the same thoroughness as the
round before it: **five of six P1s are genuinely closed**, thirteen of the
fifteen P2s, and several fixes are better than what was suggested — the
route-auth allowlist test, the `Rate` helper, `CurrencyCoverageTest` deriving
truth from `getCasts()`, and a light theme that was really tuned rather than
shuffled. The merge gate is on, and its fourteen required contexts match the
jobs that report them in both directions.

What this audit finds has one shape, and it is the previous thesis one level
deeper. Last time the guards were correct and *did not gate*; that was fixed.
This time the guards gate, and **every consequential finding sits in the blind
spot of a guard whose predicate is narrower than the rule it enforces.** The
money guard matches `.amount` and the new code names its values `…Cents`, so it
reports green over nine violations. The i18n guard matches accents and the new
literal is `1,5 h`. The a11y gate renders stories and the two failing colours
live in a route file and an unstoried state. `CurrencyCoverageTest` asserts the
column *list* while the predicate misses soft deletes. The required-status-checks
rule names jobs, and `scripts/**` turns none of them on — so the disaster-recovery
script has no lane at all. Fix the predicates, not just the findings: a guard
that reports green over a live violation is worse than no guard, because it
retires the vigilance that would have caught it.

Two findings are not of that shape and outrank everything else. Backup archives
ship world-readable with `APP_KEY` and `DB_PASSWORD` inside them, on the
documented nightly-cron path. And the same closed URSSAF period is priced two
different ways depending on which screen you open, because only the treasury
reads the contribution-rate history — so after an ACRE step ends, `/bank` and
`/declarations` disagree about a figure the user then files.

## Findings

### [P1] Backup archives are world-readable and contain `APP_KEY`, `DB_PASSWORD` and any S3 credentials

- **Where**: `scripts/opusline-backup.sh:189` (`mkdir -p "$BACKUP_DIR"`), `:203`
  (`cp "$ENV_FILE" "$work/env"`), `:213` (`tar czf`)
- **What**: The script sets no `umask` and never `chmod`s — verified, there is
  no `umask` or `chmod` anywhere in its 281 lines. The staging directory is
  fine (`mktemp -d` at `:185` is 0700); the *delivered* artefact is not.
  `./backups` is created 0755 and the archive lands at the process umask, 0644
  on every mainstream distro. Inside it, verbatim, is the `.env`: `APP_KEY`,
  `DB_PASSWORD`, and `AWS_SECRET_ACCESS_KEY` when `MEDIA_DISK=s3`. Including
  the env file is the right call and says so at `:201-202` ("Without it the
  database restores fine and nobody can log in, which is the failure mode that
  looks like a good backup") — the reasoning is sound, only the mode is wrong.
- **Why it matters**: `SECURITY.md:45` makes "keep `APP_KEY` secret and
  unchanged" one of the two things carrying a self-hoster's exposure, and
  `docs/self-hosting.md:273` recommends a nightly host cron. Any other local
  user, any container bind-mounting that directory, and any rsync/NAS share
  that preserves modes now holds every secret the instance has — and `APP_KEY`
  decrypts the TOTP secrets, recovery codes and calendar tokens in the dump
  sitting beside it in the same tarball.
- **Suggested fix** (S): `umask 077` at the top of the script, plus explicit
  `chmod 700 "$BACKUP_DIR"` / `chmod 600 "$archive"` so a pre-existing
  directory is corrected too.

### [P1] The same closed URSSAF period is priced two ways, and only the treasury reads the rate history

- **Where**: `apps/api/app/Domain/Bank/Actions/ComputeBankProvisions.php:411,424`
  vs `apps/api/app/Domain/Declarations/Actions/SummarizeDeclarations.php:252,429`
  and `apps/api/app/Domain/Deadlines/Actions/PriceFiscalDeadlines.php:129`
- **What**: `ContributionRateHistory` has exactly one consumer in the whole
  app — `ComputeBankProvisions`, which prices a carried period with
  `Rate::of($base, $rates->onDate($end))`. Every other reader of a *closed*
  period — the Déclarations card, its six-month history strip, the Échéances
  pricer — calls `$settings->urssafContributionsOn($base)`, i.e. today's stored
  rate. `BankProvisionsTest.php:580` pins the correct behaviour ("prices the
  carried month at the rate that applied when it closed": July at 25.2 %,
  August at 12.2 %); there is no equivalent test under `tests/Feature/Declarations`
  or `tests/Feature/Deadlines`, and `ContributionRate::` appears in neither.
- **Why it matters**: After an ACRE step ends — the exact case the rate table
  was built for — the same 2026-07 declaration reads 41 580 on `/api/bank` and
  20 130 on `/api/declarations?period=2026-07`. Worse,
  `SummarizeDeclarations::coveredCarry()` (`:304`) matches the treasury's
  historically-priced carry against the screen's today's-rate total, so the
  "the compte pro covers this return" indicator is computed from two different
  numbers for one period. The user files one of them.
- **Suggested fix** (M): Give `SummarizeDeclarations` and `PriceFiscalDeadlines`
  the same `ContributionRateTimeline`, and move the choice ("running period →
  lines; closed period → historical rate") into one helper beside
  `urssafContributionLines()` so a third caller inherits it.

### [P1] The 2042-C PRO's versement-libératoire box is priced with today's settings for a whole past year

- **Where**: `apps/api/app/Domain/Declarations/Actions/SummarizeAnnualDeclarations.php:76,84,87`
- **What**: `liberatingPaid` sums `Rate::of($base, $settings->liberating_payment_rate_bp)`
  over every URSSAF period of the shown year, and both `box` and the null-check
  read `$settings->liberating_payment` — all live settings — while `$year` comes
  from `$monthStart->year`, which the user navigates freely into past years
  (`SummarizeDeclarations.php:79-86` rejects only the running month and later).
  Nothing historizes the VL flag: `ContributionRate` stores only
  `effective_rate_bp`, so unlike the URSSAF rate this cannot be reconstructed
  after the fact. `DeclarationsAnnualTest.php:50` only covers the flag being
  constant for the year.
- **Why it matters**: A freelancer who switched the versement libératoire on in
  July 2026 gets a 2026 return claiming VL was paid on January–June too, with
  the receipts routed to box 5TE instead of 5HQ for the whole year. That is a
  wrong tax return, produced confidently.
- **Suggested fix** (M): Record the VL flag and rate alongside the contribution
  rate (extend `ContributionRate` / `RecordContributionRate`) and read the
  year's periods off that timeline; for years with no recorded history, fall
  back to today's settings but suppress the claim rather than asserting it.

### [P1] The money guard keys on `.amount` and catches none of the nine violations written since — third audit running

- **Where**: guard at `apps/web/src/lib/money-arithmetic.test.ts:47-71`;
  offenders at `features/expenses/lib/vat.ts:74,79,85,100,106`,
  `features/expenses/components/expense-trend-card.tsx:33`,
  `features/expenses/components/subscription-form.tsx:409`,
  `features/expenses/components/expense-calc-box.tsx:144`,
  `features/expenses/lib/subscription-draft.ts:115`,
  `features/declarations/lib/labels.ts:65`,
  `features/declarations/components/cfe-amount-dialog.tsx:69`,
  `features/settings/lib/settings-form.ts:369`,
  `features/treasury/components/record-transfer-dialog.tsx:117`
- **What**: The three violations the last audit named are genuinely fixed, and
  the fix went further than asked — `projectMissionMonth` now takes the
  account's real `contributionRateBp`, and `deadline-timeline.tsx:301` reads
  `fiscal.base.amount` off a DTO field that was added for it. But the guard
  built to stop the next regression is an AST matcher that flags a `*`/`/`/`%`
  binary expression only when an operand *syntactically contains* a `.amount`
  member read. Every violation above names its money `…Cents`, or reads
  `.amount` one statement earlier, so the walk returns false. All nine were
  checked by hand against the matcher: zero are flagged.
  `expense-trend-card.tsx:33` divides a `reduce`d sum of `point.ht.amount` by
  `points.length` — the `.amount` read lives in the map on line 27, one
  statement away. `subscription-form.tsx:409` does
  `Math.round(amounts.ttcCents / 12)`, duplicating
  `Subscription::monthlyProvisionOn()` (`divide(12, ROUND_HALF_UP)`), which the
  API already ships as `SubscriptionData.monthlyProvision`.
- **Why it matters**: This class has now appeared in all three audits. The
  guard was the whole remediation, and it reports green over a broken
  invariant — which is worse than no guard, because it retires the vigilance
  that would otherwise catch it in review. The drift direction is perverse:
  *better-named* code (`ttcCents` over `x.amount`) escapes more reliably.
- **Suggested fix** (M): Widen the matcher from "reads `.amount`" to "is a
  money value" — match identifiers and properties against `/Cents$|^cents$/i`
  as well as `.amount`, and taint through single-assignment locals. Then close
  the nine: delete the ones the API already answers, move genuine projections
  into `lib/billing.ts` beside `projectMissionMonth`, and add the rest to
  `SANCTIONED_FILES` only with a written reason.

### [P1] The treasury bar silently drops the subscriptions provision

- **Where**: `apps/web/src/features/treasury/lib/bands.ts:32-35,42`;
  `features/treasury/lib/band-skins.ts:20-48`;
  `features/treasury/components/treasury-breakdown.tsx:28`
- **What**: `TreasuryBandKey` covers `vat | urssaf | cfe | buffer | transferable`.
  The API's `BankProvisionsData` carries a fifth kind, `subscriptions`
  (`types.gen.ts:155`), computed by `ComputeBankProvisions::subscriptions()`
  (`:448-483`) and summed into `provisions.total` at `:103`. `treasuryBands`
  scales every ratio against `held = data.provisions.total.amount` — which
  includes it — while never emitting a band for it, and
  `treasury-breakdown.tsx:28` destructures only `{ vat, urssaf, cfe }`.
- **Why it matters**: The stacked bar has an unlabelled gap exactly the size of
  the subscriptions provision, and the screen whose entire job is explaining
  where the balance went never names that money. The last audit predicted this
  in these words: *"a fifth provision kind would be silently dropped from both
  the bar and its denominator."* The API then added the fifth kind.
- **Suggested fix** (S): Add `subscriptions` to the key, the skins and the
  tuple, with a message key. Then make the omission impossible — derive the
  tuple from `Object.entries(data.provisions)` minus `total`, or assert in
  `bands.test.ts` that the ratios sum to 1.

### [P2] Soft-deleted expenses hold money the currency lock cannot see

- **Where**: `apps/api/app/Domain/Users/Models/User.php:294`
  (`$this->expenses()->exists()`), `app/Domain/Expenses/Models/Expense.php:80`
  (`use SoftDeletes`), `app/Domain/Expenses/Actions/DeleteExpense.php:34`
- **What**: Found independently by two reviews. `Expense` is the only
  money-carrying model with `SoftDeletes`. `DeleteExpense` force-deletes a
  hand-entered purchase but soft-deletes a subscription debit (deliberately —
  the tombstone stops re-materialisation). `hasLockedCurrency()` asks
  `$this->expenses()->exists()`, which `SoftDeletingScope` filters, and
  `DeleteSubscription` hard-deletes with `nullOnDelete`, so the tombstone
  survives with `subscription_id = NULL`. An account whose only stored amounts
  are deleted subscription debits reads as "currency not locked", and
  `ChangeAccountCurrency` flips it to USD while `expenses.currency = 'EUR'`
  rows still hold cents. `CurrencyCoverageTest` cannot catch this: it asserts
  the column *list*, not that the predicate witnesses those columns.
- **Why it matters**: The predicate's stated guarantee — *"every stored amount
  provably shares one currency and aggregations never have to guard against a
  mix"* (`User.php:262-266`) — is false. Blast radius is currently zero because
  nothing reads tombstone money, but this is precisely the silent drift that
  the last audit's P1-5 was, re-introduced by the new domain.
- **Suggested fix** (S): `->withTrashed()->exists()`, and extend
  `CurrencyCoverageTest` to assert the predicate ignores no scope.

### [P2] `GET /expenses` and `GET /subscriptions` write, take the account row lock, and rescan every subscription debit ever created

- **Where**: `apps/api/app/Domain/Expenses/Actions/MaterialiseSubscriptionOccurrences.php:26-45`
  (scan at `:39`), called from `ListExpenses.php:65` and `ListSubscriptions.php:51`
- **What**: Both list endpoints materialise before reading. With ≥1 active
  auto-creating subscription that opens a transaction, takes `User::lockRow()`
  — a `SELECT … FOR UPDATE` on the users row — then runs
  `$user->expenses()->withTrashed()->whereNotNull('subscription_id')->toBase()->get(...)`,
  hydrating **every subscription-generated expense the account has ever had**,
  tombstones included. On top, `OccurrenceSchedule::debitsBetween()` iterates
  from each subscription's first debit to today: 120 turns for a ten-year-old
  monthly subscription, per subscription, per request.
- **Why it matters**: Two costs that grow linearly with account age sit on the
  two hottest read paths of the new domain, and they serialize — the SPA
  fetches `/expenses` and `/subscriptions` together, so the second blocks on
  the first's `FOR UPDATE`. A read endpoint holding a write lock can never be
  served from a replica, and under Octane a lock wait pins a worker. On SQLite
  the whole file is the lock.
- **Suggested fix** (M): Bound the idempotency probe to the window being
  materialised and back it with a covering index; move materialisation off the
  read path onto the existing scheduler (`RetireDormantWork` shows the
  pattern). If on-read must stay, gate it on "a period boundary has passed
  since `updated_at`" so the common request does no work and takes no lock.

### [P2] Every expense mutation replays the entire journal read, lock included

- **Where**: `apps/api/app/Http/Expenses/Controllers/ExpenseController.php:43,55,67,78,96,107,118`
- **What**: Eight endpoints return `$listExpenses->handle(...)` as their
  response body. `ListExpenses::handle()` is ~14 queries plus the full
  materialisation pass above. Several of those mutations already took
  `User::lockRow()` in their own transaction (`CreateExpense.php:26`,
  `DeferVatDeductions.php:26`, `ReintegrateVatDeduction.php:23`), so the
  request acquires and releases the account row lock **twice**.
- **Why it matters**: Recategorising two expenses costs a full screen load, and
  the double acquisition doubles the window in which a concurrent write from
  the same account blocks. This is what turns the previous finding from "one
  slow screen" into "every interaction on the screen".
- **Suggested fix** (S–M): Return the mutated `ExpenseData` or a narrow delta
  and let the SPA invalidate — the TanStack Query idiom the rest of the app
  already uses. At minimum, skip materialisation inside `ListExpenses` when the
  caller just ran it.

### [P2] A bank import rescans the whole account in PHP, inside the user row lock

- **Where**: `apps/api/app/Domain/Bank/Actions/ImportBankStatement.php:123-129`;
  `app/Domain/Expenses/Actions/SuggestExpenseMatches.php:34-51`
- **What**: After the chunked insert, the import hydrates every credit the
  account has ever imported that is unlinked and unmatched (no date bound),
  then calls `suggestExpenseMatches->handle($locked)` with no `$spentFrom`,
  whose own docblock says null means "the whole account" — every unlinked debit
  ever, plus every expense with no bank movement ever, cross-matched in PHP.
  All inside the transaction holding `User::lockRow`.
- **Why it matters**: The code two blocks earlier already documents this exact
  failure mode — *"a first import carries years of history, and N round trips
  under the user row lock can outlive Octane's `max_execution_time`"* — and the
  rescan added afterwards reintroduces the shape in memory rather than in round
  trips. A timeout leaves the lock held and the statement half-reconciled.
- **Suggested fix** (M): Pass the statement's `period_start` minus
  `SuggestExpenseMatches::DAYS_APART` as `$spentFrom` and bound `$suggestible`
  to the same window; if full re-evaluation is a product requirement, queue it
  outside the lock.

### [P2] `Ca3Chain` replays from a user-chosen, unbounded first month on every call

- **Where**: `apps/api/app/Domain/Declarations/Vat/Ca3Chain.php:36`; anchored by
  `Ca3ChainStart.php:38-47`; bounded only by `CivilMonth.php:21`
  (`EARLIEST_DAY = '1900-01-01'`)
- **What**: `boxes()` has no memo — it loops month by month from `firstMonth`
  on every call. With no CA3 ever marked declared, the chain anchors on
  `min(business_started_on, first paid invoice, first expense)`, and
  `$user->expenses()->min('spent_on')` is user input validated only as
  "≥ 1900-01-01 and ≤ account today". Each iteration calls `CollectedInvoices::htCents()`
  and `vatCents()`, which are `array_filter` passes over every collected row.
  `boxes()` is called ~14× in `ComputeBankProvisions::vat`, twice in
  `SummarizeDeclarations`, six times in `history()`.
- **Why it matters**: One expense back-dated to 1900 turns `/api/declarations`,
  `/api/bank` and `/api/expenses` into ~22 × 1,500 month-iterations each
  scanning the full invoice array — tens of millions of comparisons per
  request, on a long-lived Octane worker, repeatable at will by the account
  holder. Availability only, no correctness impact.
- **Suggested fix** (S/M): Clamp `Ca3ChainStart` to the horizon callers need
  (`CARRY_LOOKBACK_MONTHS` already exists) and memoize `boxes()` per month.

### [P2] Unbounded id arrays and credential blobs at the request boundary

- **Where**: `apps/api/app/Domain/Expenses/Data/ExpenseSelectionData.php:22-36`,
  `RecategorizeExpensesData.php:20-32`, consumed at `SelectExpenses.php:26-31`;
  `PasskeyLoginData.php:17-18`, `RegisterPasskeyData.php:21-22`,
  `TwoFactorChallengeAnswerData.php:24-25`
- **What**: `expenseIds` carries `#[ArrayType, Min(1)]` and per-item `integer`,
  but no `#[Max]` on the array. `SelectExpenses` then runs `whereIn('id', $ids)`
  over whatever arrived. A body near `post_max_size` carries ~10⁶ ids: on
  Postgres that blows the 65,535 bind-parameter ceiling into a driver
  exception — a 500 rendering the query under `APP_DEBUG`; on MySQL it is a
  multi-megabyte statement plus the result memory. Both routes sit behind only
  `throttle:api` (120/min). Same class: the three `#[Json]` credential strings
  have no `#[Max]`, so the two *unauthenticated* passkey routes `json_decode`
  an arbitrary body twice. A real credential is ~1 KB.
- **Why it matters**: Authenticated DoS plus a 500 that leaks internals —
  exactly the bound the last audit asked for on ints and strings, now missing
  on the new arrays.
- **Suggested fix** (S): `#[Max(500)]` on the two arrays, `#[Max(8192)]` on the
  three credential strings.

### [P2] The ownership half of the authorization model has no executable guard

- **Where**: `apps/api/app/Domain/Shared/Routing/OwnedRouteBinding.php:18-21`;
  `tests/Unit/ArchitectureTest.php:7-20`; `tests/Feature/RouteAuthenticationTest.php:36`
- **What**: All 15 route parameters were traced. Eleven bind models and all
  eleven override `resolveRouteBinding` through `OwnedRouteBinding`;
  `{document}` is an int re-scoped via `documentOf()`; the rest are
  regex-constrained scalars. The invariant holds today, and nothing asserts it.
  `RouteAuthenticationTest` checks the *guard* only — a new
  `Route::get('/x/{foo}')` whose model forgets `resolveRouteBinding` is a
  silent cross-tenant read with the whole suite green.
- **Why it matters**: With no policy layer, this override *is* the
  authorization. It is a one-method-per-model convention protecting all tenant
  data, currently held together by memory — the same argument that made the
  auth-on-routes test the last audit's highest-value single test.
- **Suggested fix** (S): Reflect over `Route::getRoutes()`, resolve each
  parameter's bound model, assert it declares `resolveRouteBinding` or sits
  under a `scopeBindings()` parent that does.

### [P2] The disaster-recovery script ships in every release with no lane, no test, and a restore that runs against a live stack

- **Where**: `scripts/opusline-backup.sh:237-271` (`load_database:83`);
  `.github/workflows/ci.yml:59-112` (no path filter matches `scripts/**`);
  `release-please.yml:198` (uploaded as a release asset);
  `docs/self-hosting.md:260`
- **What**: Two problems in the same file. (a) No lane filter lists `scripts/`,
  so a PR that only edits the backup script turns on zero lanes — it runs the
  repo guards, the secret scan and the title check, none of which execute it.
  The `docker` lane boots the real stack but never calls `backup`, `verify` or
  `restore`. (b) `load_database` pipes `pg_dump --clean --if-exists` into
  `psql` with no `compose stop`, while `api` (Octane workers), `queue` and
  `scheduler` hold open connections and can write between the DROPs and the
  reload; the docs advertise restoring "into a stack that is up".
- **Why it matters**: This is the only documented recovery path for an app
  holding invoices, URSSAF declarations and imported bank movements, and
  `docs/self-hosting.md:288` tells operators *"Check a restore before you need
  one"* — advice the project does not follow for itself. A restore is run under
  stress, once, and the failure mode (a worker writing into a half-restored
  schema, or a DROP blocking on a lock until the command appears to hang) is
  the worst possible moment to discover it.
- **Suggested fix** (M): Add `'scripts/**'` to the `docker` lane and one job
  that runs backup → `down --volumes` → `up -d` → restore → assert a row
  survives. Wrap `load_database`/`extract_storage` in
  `compose stop api queue scheduler` … `compose up -d`.

- **Suggested fix** (S): Add `'scripts/**'` to the `web` lane, or an always-on

### [P2] The euro↔cents conversion has leaked out of `lib/billing.ts` into three implementations

- **Where**: sanctioned `lib/billing.ts:288,318`; leaked
  `features/settings/lib/settings-form.ts:367-369`,

- **What**: All three do `parseDecimal(locale, draft)` then

- **Suggested fix** (S): One `parseAmountToCents(locale, draft, { allowZero })`

## Aligned-and-healthy

Protect these. Several are better than the last audit found them, and several
are things most projects this size never get right.

- **The route-auth allowlist test is the right shape.**
  `RouteAuthenticationTest.php:36-55` enumerates every `api/*` route and asserts
  the set *not* behind `auth:sanctum` equals exactly the eight documented
  entries, each carrying its justification. It inverts the assertion, so a new
  public route fails the build. This closed the last audit's highest-value
  finding properly rather than minimally.
- **The new security domains are genuinely well built.** TOTP replay protection
  refuses any step ≤ the last used, persisted under `User::lockRow` inside a
  transaction, with a test named "a code that already answered cannot answer
  again". The pending-login state machine is bounded on three independent axes
  (300 s TTL, 5-failure budget, dual-key limiter per account *and* IP) with a
  deliberate `Hash::make` burn to flatten the unknown-email timing oracle.
  WebAuthn is confined to one class and round-tripped through the real library
  including forged assertions, wrong origin, wrong user handle and a replayed
  signature counter — the cases most integrations never test.
- **Secret hygiene is uniform across the new surface.** `totp_secret` and
  `two_factor_recovery_codes` are encrypted casts, the trusted-browser token
