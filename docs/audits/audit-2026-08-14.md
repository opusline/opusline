# Audit — 2026-08-14

First audit of this repository. Branch: `feat/multi-currency` (clean, one commit ahead
of `main`). Scope: `apps/api`, `apps/web`, `apps/storybook`, `packages/ui`,
`packages/api-client`, repo tooling/CI/ops. Method: orientation pass + four parallel
deep reviews + cross-cutting synthesis; the highest-stakes claims were re-verified
against source before writing this report.

## Executive summary

The codebase is unusually disciplined for a solo project: authorization is structurally
airtight, concurrency is handled with one consistent locking idiom, layering is enforced
by tooling (Biome import boundaries, Pest arch tests), the generated API client has
zero drift, and story coverage is effectively 100%. The findings cluster in three
places. First, **the money/time valuation layer has three sources of truth that
disagree** — the CRA clamps overtime to one day, the invoice valuation does not, and
the browser computes its own "Montant facturable" with float math. Second, **two core
invariants stated in TODO.md are silently violated**: billing mode is freely mutable on
missions with entries, and fiscal dates are computed in UTC with no account timezone.
Third, **the verification and onboarding layer lies**: Turbo task hashes are blind to
`packages/ui` source (stale green tests locally *and* in CI), and every README is stock
template text on an AGPL project. The one thing to fix first is billing-mode
immutability — it is the single highest-leverage data-integrity gap and sits directly
on the CRA-export v1 milestone, as do findings P1-2 through P1-5.

## Findings

### [P1] Billing mode is freely mutable on a mission that already has time entries

- **Where**: `apps/api/app/Domain/Missions/Actions/ValidateMission.php:23-60`,
  `apps/api/app/Domain/Missions/Actions/UpdateMission.php:27-42`,
  `apps/api/tests/Feature/Missions/MissionUpdateTest.php:40-55`
- **What**: The only mode-related guard blocks leaving day-fraction billing when a
  **CRA** exists; nothing checks `timeEntries()`. `UpdateMission` writes `billing_mode`
  unconditionally, and a test named *"changes the billing mode"* locks the flip in as
  intended behavior. TODO.md:26-29 states the mode is immutable once the mission has
  entries ("new contract = new mission").
- **Why it matters**: The unit of `duration_minutes` is *derived* from the mission's
  mode. Flipping Daily → Hourly on months of entries silently reinterprets `rate_cents`
  from €/day to €/hour on every historical entry (a 550 €/j mission with 60 tracked
  days becomes 550 €/h × 420 h). `BillingMode::resolveCraRequired()`
  (`apps/api/app/Domain/Missions/Enums/BillingMode.php:32-39`) also force-clears
  `cra_required`, so the mission drops off the CRA "à produire" list and every issued
  CRA's tracked-vs-reported écart becomes noise.
- **Suggested fix** (S): Add an entries guard to `ValidateMission` mirroring the
  existing CRA guard; rewrite the test to assert the 422. Decide whether Hourly↔Fixed
  transitions need the same treatment.

### [P1] Overtime day-fraction clamp is applied in the CRA path but not the money path

- **Where**: Clamped: `apps/api/app/Domain/Cra/Actions/MaterializeCraDays.php:130-146`
  (`min(..., CraDay::FULL_DAY_BP)`, rule documented and tested at
  `tests/Feature/Cra/CraMaterializationTest.php:28`). Not clamped:
  `apps/api/app/Domain/Invoices/Actions/ValueTrackedTime.php:74-80`,
  `apps/api/app/Domain/TimeEntries/Models/TimeEntry.php:89-99`.
- **What**: On the defaults (`workday_minutes = 420`, half-day rounding), 8h tracked in
  one day yields **1,0 j** on the CRA but **1,5 × TJM** from `ValueTrackedTime` and
  **1,5 j** in the week view. "A client is billed days, not overtime" is a stated
  product rule applied in one of the two places that need it — and the money side is
  the untested one.
- **Why it matters**: The invoice dashboard's "à facturer" total and the CRA's "Total à
  facturer" disagree on any day longer than the workday, and the divergence favors the
  larger number. The CRA is the document the client signs.
- **Suggested fix** (S): Apply the same per-day clamp in `ValueTrackedTime` and
  `TimeEntry::valuedDayFraction`, with unit tests locking both to the CRA figure.

### [P1] The frontend computes money — twice

- **Where**:
  - `apps/web/src/features/timer/lib/rounding.ts:102-121` — `billableAmountCents()`
    ends in `Math.round(quantity * mission.rate.amount)` where `quantity` is a float
    (`minutes / 60` or `minutes / workdayMinutes`). Rendered as `"Montant facturable"`
    in `apps/web/src/features/timer/components/timer-stop-dialog.tsx:246-255`.
    `rounding.test.ts:141` asserts `29_071` cents — a figure that exists only in the
    browser; the stop payload sends `durationMinutes` + `rounding` and the server
    derives money itself.
  - `apps/web/src/features/invoices/lib/grouping.ts:86-99` — `groupByClient()` sums
    `amountTtc.amount` into a per-client total the API does not expose, rendered as an
    authoritative figure in `invoices-table.tsx:97-100`. No currency check while
    summing. No test file.
- **What**: Direct violation of the cross-cutting decision "the frontend NEVER does
  money arithmetic — totals always come from the API" (TODO.md:14-21).
- **Why it matters**: The stop dialog can promise a cent the server will not record
  (different rounding mode, float vs rational division on a 450-minute workday), and
  the label makes it a claim, not an estimate. The client-side TTC sum is exact today
  but is the precedent the invariant exists to prevent, on the screen v1.1 builds on.
- **Suggested fix** (M): Have the stop endpoint return a preview amount per rounding
  option (or drop the amount and show only the billed quantity, which
  `provisionalBilledLabel` already produces); add a per-client total to the invoice
  list/summary payload so `groupByClient` only groups and orders.

### [P1] Every fiscally load-bearing date is computed in UTC; no account timezone exists

- **Where**: `apps/api/config/app.php:82` (`'timezone' => 'UTC'`); no timezone column
  in `user_settings`; no `setTimezone` call in `app/`. `CarbonImmutable::today()`
  consumers: `Domain/Invoices/Actions/PayInvoice.php:27-29`, `CreateInvoice.php:29-31`,
  `RecordInvoiceEvent.php:22`, `Domain/Invoices/Models/Invoice.php:176-180`,
  `Domain/Cra/Actions/SendCra.php:55`, `AttachSignedCra.php:44`, `ValidateCra.php:31`,
  `ListCras.php:120`, `RenderCraPdf.php:157`; plus `BeforeOrEqual('today')` in
  `Domain/Invoices/Data/PayInvoiceData.php:145-153` and `CreateInvoiceData.php:45-46`.
- **What**: For a French user, "today" is wrong for the first 1-2 hours of every day.
- **Why it matters**: Marking an invoice paid at 00:30 Paris on 1 January stores
  `paid_on = 31 December` — the wrong URSSAF/TVA declaration period on a cash basis,
  exactly the failure mode `PayInvoiceData`'s own docblock warns about. The same window
  rejects a user-supplied `paidOn` of *their* today as "in the future" (422), and dates
  a CRA sent at 00:30 on the 1st into the previous month.
- **Suggested fix** (M): Add a `timezone` user setting and resolve every "today"
  through it. Small per-site change; touches every call site above, so it gets cheaper
  the sooner it lands. Pair with the web-side TZ test finding below.

### [P1] CRA optimistic day write is never rolled back on failure

- **Where**: `apps/web/src/routes/_authed/cra.tsx:47-70` (`applyDaysToCache`),
  `:137-145` (`onMutate` applies, `onSuccess: refreshCras`, `onError` only sets a
  message — no rollback, no `invalidateQueries`, no `onSettled`).
- **What**: The optimistic write itself is deliberate and well-justified (the
  double-click coalescing comment at `:131-136`, tested in
  `features/cra/lib/cra-cache.test.ts`). But after a rejected write the grid keeps
  rendering the refused day until the query goes stale (`staleTime: 30_000`) or the
  window refocuses. Meanwhile `cra-page.tsx:207-247` renders the optimistic `model`
  next to API-sourced `reportedDays`, and `cra-document.tsx:193-236` renders optimistic
  per-week subtotals above an API-sourced grand total.
- **Why it matters**: On the v1-differentiator screen, a failed write shows an error
  banner *and* a grid that contradicts it, while the PDF is generated from the server's
  state.
- **Suggested fix** (S): `onSettled: refreshCras`, or restore from the `onMutate`
  context in `onError`.

### [P1] Turbo task hashes are blind to `packages/ui` (and partly `api-client`) source

- **Where**: `turbo.json:5-10,47-55`, `apps/storybook/turbo.json:3-8`;
  `packages/ui/package.json:6-8` and `packages/api-client/package.json:12-15` define no
  `build` script.
- **What**: `test`, `check-types`, `lint` declare no `dependsOn`; `build` declares
  `^build`, but a `^task` edge to a package that doesn't define that task contributes
  nothing to the hash, and workspace links resolve as constant `link:` strings. The
  hash for `@opusline/web#check-types`, `#test`, `#build` and
  `@opusline/storybook#build:storybook` includes no byte of `packages/ui/src`.
  `web#test`/`#check-types` are equally blind to `api-client` (only `web#build` has the
  explicit generate edge). The repo's own Turborepo skill notes flag exactly this
  pattern (`.agents/skills/turborepo/references/configuration/gotchas.md:205-219`).
- **Why it matters**: A PR that only changes `packages/ui` replays pre-change
  test/type-check results — in the pre-push hook and in CI, both reading the same
  remote cache. A breaking design-system change ships green and surfaces only when
  someone later touches `apps/web`. This undermines every other guarantee the repo's
  strong CI otherwise provides.
- **Suggested fix** (S): Add a `transit` task (`"transit": { "dependsOn": ["^transit"] }`)
  and point `test`, `check-types`, `lint`, `build`, `build:storybook` at it.

### [P1] `--palette-*` tokens are never redefined for dark mode — 7 of 8 fail WCAG AA in the default theme

- **Where**: `packages/ui/src/styles/globals.css:72-79` (`:root` only), `:82-141` (the
  `.dark` block redefines every other token but no `--palette-*`), `:194-201`
  (`@theme inline` maps both themes to the same light-tuned hex). Consumer:
  `apps/web/src/lib/palette.ts:27-35` uses them as text colors.
- **What**: Measured against the dark background `#171412`: plum 2.66:1, indigo 2.75:1,
  slate 3.27:1, stone 3.52:1, terracotta 3.55:1, sage 3.79:1, olive 3.98:1 — all below
  4.5:1. Only amber passes, and index 0 is already special-cased to `text-primary-text`,
  so in practice every palette hue used as text is sub-AA in dark mode. Storybook's
  default theme is dark (`apps/storybook/.storybook/preview.ts:31`).
- **Why it matters**: Client/mission labels — the palette's entire purpose — are the
  least legible text in the product's default theme. CLAUDE.md declares accessibility
  non-optional.
- **Suggested fix** (S): A `--palette-*` block inside `.dark` with lightness-lifted
  variants, as already done for `--primary-text`, `--link`, `--destructive`. Not an
  opacity tweak at call sites.

### [P2] Timer stop materializes a fully client-supplied duration

- **Where**: `apps/api/app/Domain/Timers/Actions/StopTimer.php:21-37`,
  `Domain/Timers/Data/StopTimerData.php:20-31` (`Between(1, 1440)` only);
  `RunningTimer::elapsedSeconds()` (`Domain/Timers/Models/RunningTimer.php:56-65`) is
  read by display/pause/trim but nothing in the stop path.
- **What**: The timer is server-authoritative for existence, start time, and
  one-per-user — but not for the number that becomes billable time.
- **Why it matters**: A regression in the web stop dialog writes wrong billable minutes
  with no server-side sanity bound. Rounding *up* from elapsed is expected (that is
  what the dialog is for); accepting an arbitrary unrelated value is not.
- **Suggested fix** (S): Reject durations exceeding `ceil(elapsedSeconds/60)` rounded
  up to the coarsest offered increment. Pairs with the preview-amount fix in P1-3.

### [P2] The web test suite runs entirely in `TZ=UTC`, so the calendar-date guards cannot fail

- **Where**: `apps/web/vitest.config.ts:1-12` (`env: { TZ: "UTC" }`); no test overrides
  `TZ` or passes `timeZone` (checked across all 57 test files).
- **What**: The date layer itself is correct and well-reasoned
  (`src/lib/dates.ts:30-77`, `weeks.ts:9-13` — part-wise construction, no
  `toISOString` on local dates). But under UTC, the buggy implementation
  (`new Date("2026-08-01")`) and the correct one produce identical output, so
  `dates.test.ts:9` ("keeps a calendar date on the day the API sent") passes
  unconditionally — as do `weeks`, `months`, `repeat-week`, and the timer's entry-date
  derivation (`features/timer/components/timer-provider.tsx:304-305`), the app's
  highest-risk local/UTC boundary.
- **Why it matters**: A refactor can reintroduce the exact bug the comments warn about
  and the suite stays green; an entry lands on the wrong fiscal day, a CRA day crosses
  a month boundary.
- **Suggested fix** (S): Run the date-sensitive suites under one negative and one
  positive offset (e.g. `America/Los_Angeles`, `Pacific/Auckland`) via a second vitest
  project or `describe.each` setting `process.env.TZ`.

### [P2] CI's PHP-free JS job silently depends on the PHP generate task

- **Where**: `.github/workflows/ci.yml:24-41`; `turbo.json:32-46`;
  `apps/api/scripts/php.sh` / `bootstrap.sh`.
- **What**: `turbo run test check-types build "--filter=!@opusline/api"` does not prune
  `@opusline/api#generate` — it stays in the graph as a transitive `dependsOn` of
  `web#build`. The job passes today only via a remote-cache hit seeded by the
  maintainer's own pre-push hook (verified in CI run 31812612641: "cache hit, replaying
  logs"). On any miss, the JS job tries to boot Composer-in-Docker plus the full Sail
  stack (MySQL, Redis, MinIO) and fails after minutes. Fork PRs get no `TURBO_TOKEN`,
  so for them the miss is guaranteed.
- **Why it matters**: The first outside contribution to this AGPL project hits a
  broken CI wall. Cache eviction or any `turbo.json` edit breaks the maintainer's own
  runs the same way.
- **Suggested fix** (M): Let CI's JS job build from the committed `openapi.json`
  (severing the generate edge behind a flag or env), relying on the existing
  `spec-drift` job (`ci.yml:73-107`) to catch staleness — it already does the real check.

### [P2] Generate tasks declare committed source as cache `outputs`

- **Where**: `turbo.json:38-46`: `@opusline/api#generate` → `outputs: ["openapi.json"]`
  (committed, and inside the task's own default inputs); `@opusline/api-client#generate`
  → `outputs: ["src/**"]` (all committed). Related smaller drift: `web#build`
  overrides `inputs` without re-stating the stories exclusion (`turbo.json:8,35`);
  `build.outputs` lists `storybook-static/**` which no `build` task produces; `.env*`
  is an input for a package with no env files.
- **What**: Cache restores can write over checked-out, reviewed, git-tracked files, and
  each task hashes its own output so it never caches usefully.
  `scripts/generated-artifacts.sh:17-18` already bypasses turbo for the drift check —
  the right instinct, unstated in config.
- **Why it matters**: `turbo` mutating tracked files on a cache hit is a
  hard-to-diagnose class of surprise; the config claims cacheability it doesn't have.
- **Suggested fix** (S): `"cache": false` on both generate tasks; tidy the three input
  inconsistencies while there.

### [P2] `workday_minutes` is a global env constant, not an account setting

- **Where**: `apps/api/config/app.php:125` (`env('APP_WORKDAY_MINUTES', 420)`);
  consumed by `MaterializeCraDays.php:24-29`, `ValueTrackedTime.php:26-31`,
  `TimeEntry.php:95-99`. Also absent from `apps/api/.env.example`, along with
  `MON_ENTREPRISE_URL` / `MON_ENTREPRISE_ENABLED` (`config/services.php:47-48`).
- **What**: A business parameter with exactly the properties TODO.md:20-24 reserves for
  user-editable settings lives in `.env`, undocumented. Changing it retroactively
  rewrites every `trackedDays` figure and unbilled amount across history — including
  écarts against CRAs the client already holds. `EntryRounding.php:53-69` divides it by
  steps-per-day with `(int) round(...)`, exact only when divisible by 4 (420 yes,
  450 no).
- **Why it matters**: A deployment silently assumes a 7-hour workday and calls a live
  external URSSAF API with no discoverable knob.
- **Suggested fix** (M): Promote to `user_settings` (seeded 420) and decide the
  retroactivity semantics explicitly; document the remaining env vars in
  `.env.example`.

## Aligned-and-healthy

Protect these as the codebase grows:

- **Authorization is structural, not per-endpoint discipline.** Every route-bound model
  goes through `OwnedRouteBinding` (foreign rows 404), `Exists`/`Unique` rules carry
  `WhereConstraint('user_id', …)`, mission routes use `scopeBindings()`. No unscoped
  read or write was found.
- **One consistent concurrency idiom.** `LockUserTimer`/`LockInvoice`/`LockCra` share
  the same shape (serialize on the user row, refresh inside the lock, then guard), with
  DB uniques backing the application checks and the 23000 races handled.
- **Layering enforced by tooling.** `apps/web/biome.jsonc` makes feature isolation a
  lint error; Pest `arch()` enforces Domain→Http direction; thin controllers with all
  writes through Actions verified across all 11 controllers.
- **The multi-currency model is coherent** — better than the docs claim: one currency
  per account, locked the moment any amount exists, re-asserted under the same row lock
  the change action takes; aggregations cannot see a mix. `Currency` being
  string-backed is a documented, tested exception to the int-enum rule.
- **The generated contract chain is pristine.** All 20 `api-client` files generated, no
  drift, lint-excluded; zero shadow types or hand-rolled API calls in the app (the two
  raw `fetch`es — Sanctum CSRF, BAN geocoder — are genuinely outside the spec).
- **Dates are constructed correctly and the reasoning is written down**
  (`lib/dates.ts`, `lib/weeks.ts`, part-wise construction, the year-0-99 trap handled);
  typed `?week=` search params validate the ISO week's actual existence, not a regex.
- **The timer is genuinely server-authoritative**, including elapsed-time extrapolation
  from `dataUpdatedAt`, a re-fetch-on-any-write-failure policy, and the note queue
  preventing an in-flight note landing on the next timer.
- **Story discipline is 100%** — 35/35 UI and 67/67 web stories conformant (CSF3,
  autodocs, title prefixes), domain-flavored sample data exactly where it belongs.
- **CI ↔ hook parity via shared scripts** — the drift check is one script used by both
  pre-push and CI; secrets handling is clean (`persist-credentials: false` everywhere,
  scoped tokens, injection-safe PR-title handling); release-please stamping is
  consistent across all four version sites.
- **Comment discipline** — the repo's comments overwhelmingly state non-recoverable
  *why*s (the CRA clamp rationale, the float-avoidance in valuation, the unescaped
  LIKE prefix, the optimistic-cache race). Keep this bar.
